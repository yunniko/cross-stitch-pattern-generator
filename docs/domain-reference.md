# Domain reference — cross-stitch charting & perceptual colour reduction

Researched 2026-09-09 for G-001 M4 (domain-expert gate). Every claim below
carries a source, or is explicitly marked as recalled/unverified. Retrieval
date for all web sources: 2026-09-09.

## 1. Chart grid conventions

- **The bold grid is every 10 squares.** This is the single load-bearing
  convention: "Bold grid (every 10 squares): the single most useful feature,
  enabling counting by tens rather than laborious single-stitch counting."
  (https://stitchthis.io/blog/cross-stitch-pattern-symbols-and-notation-guide)
  Corroborated independently: darker lines every 10 stitches on commercial
  charts (https://www.fatquartershop.com/how-to-read-a-cross-stitch-pattern);
  PCStitch bolds every 10th grid line by default
  (https://sirithre.com/pcstitch-basics-turning-pixel-art-into-cross-stitch/).
- **A secondary every-5 tier is a real, but optional, feature — not the
  primary convention.** Stitch Fiddle's chart settings highlight "every 5th
  and 10th grid line" by default and expose both intervals as separately
  configurable line thickness/colour
  (https://www.stitchfiddle.com/en/help/1pdw-7v0u6b/lines). MacStitch/
  WinStitch exposes a generic "thick/thin line width" pair, i.e. **two**
  tiers, not three
  (https://www.ursasoftware.com/help/2014_en/filemenu/print/print.html and
  its 2023 Styles tab docs).
  → Three tiers (1/5/10) is defensible and matches at least one real chart
  program's default, but it is *not* what most published cross-stitch charts
  look like; two tiers (thin + bold-every-10) is the mainstream.
- **Aida fabric itself has no woven count markers.** Plain Aida is undifferentiated
  cloth. The gridded variants — Zweigart Easy Count, DMC Easy Count Magic Guide —
  carry a printed/woven wash-out grid where "each grid square counts out 10
  points", i.e. **10, never 5**
  (https://www.stitchtastic.com/store/dmc-magic-guide,
  https://www.chartingcreations.com/index.php?main_page=index&cPath=20_86).
  → Any project text claiming the 1/5/10 weights mirror "standard Aida-fabric
  count markings" is factually wrong; plain Aida has none, gridded Aida is 10.
- **Centre markers are conventional and near-universal.** Arrows or triangles
  on the outer edges of the grid, two horizontal + two vertical; where their
  lines cross is the design centre, and that is the conventional starting
  point (https://stitchthis.io/blog/cross-stitch-pattern-symbols-and-notation-guide,
  https://www.caterpillarcrossstitch.com/blogs/blog/how-to-read-a-cross-stitch-pattern).
  MacStitch prints them by default: "the centre lines of the design are marked
  with an arrow"
  (https://www.ursasoftware.com/help/2014_en/filemenu/print/print.html).
- **Row/column numbering along the chart edges is standard chart-software
  output.** MacStitch: "'Row/Column' marks the edges of chart with row and
  column numbers", with a configurable start value
  (https://www.ursasoftware.com/help/2014_en/filemenu/print/print.html).
- **Pagination: never split a 10×10 block across a page boundary**; multi-page
  charts need predictable, consistent page boundaries and overlap indicators
  (grey bands / repeated rows)
  (https://patternkeeper.app/for-designers/,
  https://stitchthis.io/blog/cross-stitch-pattern-symbols-and-notation-guide).
- **Printed symbol density norm: ~8 symbols per inch.** MacStitch: "Magazine
  normally print at about 8 symbols per inch"
  (https://www.ursasoftware.com/help/2014_en/filemenu/print/print.html).
  → ~60 stitches across a Letter/A4 printable width (~7.5 in). Anything wider
  than ~60 stitches cannot be printed at conventional density on one page.

## 2. Symbol design conventions

- **One unique symbol per thread colour** is the base rule
  (https://doodlecraftdesign.co.uk/pages/understanding-chart-symbols-for-cross-stitch-blackwork).
- **Symbol density should track colour value**: "A well-designed chart chooses
  symbols that are easy to tell apart, with denser/darker symbols for darker
  colors so the chart visually echoes the finished piece"; filled shapes for
  darker threads, outlined shapes for lighter
  (https://stitchthis.io/blog/cross-stitch-pattern-symbols-and-notation-guide).
- **Confusable symbols are the #1 documented complaint about pattern PDFs.**
  "The most common complaint about cross stitch PDFs — across forums, Reddit,
  and FlossTube — is symbols that are too similar to each other. If you need to
  zoom to 200% to tell two symbols apart, the chart has a problem."
  "Look-alike symbols for adjacent colors can cause your eye to blur them
  mid-row and you may stitch the wrong shade — one of the quietest causes of
  stitching mistakes."
  (https://stitchmate.app/guides/cross-stitch-pattern-pdf-quality — reached via
  search snippet; direct fetch returned HTTP 403,
  https://stitchthis.io/blog/cross-stitch-pattern-symbols-and-notation-guide)
  No source found that publishes a canonical banned-pairs list; the specific
  confusable pairs below are *analytical*, from typographic reasoning at 7–14 px
  render sizes, not from a cited chart-design standard.
- **Three chart styles exist and are all real**: pure symbol (B&W), colour-block,
  and symbol-on-colour — the last is called "the modern default for digital
  patterns and the most foolproof"
  (https://stitchthis.io/blog/cross-stitch-pattern-symbols-and-notation-guide).
- **The value of the B&W variant is that it prints cleanly, uses less ink, and
  can be highlighted over** as work progresses; many stitchers print the B&W
  version specifically to mark off completed blocks with a highlighter
  (https://stitchmate.app/guides/how-to-read-cross-stitch-pattern,
  https://www.fatquartershop.com/how-to-read-a-cross-stitch-pattern).
  → A B&W chart whose cells are flooded with dark grey defeats all three.

## 3. Legend / key conventions

- Standard legend row format: **symbol | brand + colour number | colour name |
  swatch | skeins needed | stitch count**
  (https://stitchthis.io/blog/cross-stitch-pattern-symbols-and-notation-guide,
  https://www.crossstitchboutique.com/cross-stitch-pattern-symbols-meaning-complete-guide-2025/).
  Strand count is given either in the legend, in pattern notes, or in brackets
  next to the symbol
  (https://cross-stitched.com/en-us/pages/how-to-read-cross-stitch-pattern).
- **Legends should be sorted by colour value, not by symbol shape**, so gradient
  progressions read in order
  (https://stitchthis.io/blog/cross-stitch-pattern-symbols-and-notation-guide).
- Charts conventionally state **design size in stitches (w × h) and finished
  size on the intended fabric count**
  (https://www.caterpillarcrossstitch.com/blogs/blog/how-to-read-a-cross-stitch-pattern).
- Backstitch / French knots / beads get their own legend notation
  (dashed lines, dedicated symbols) — out of scope for a photo converter, but
  it's why real legends have a "stitch type" column.

## 4. Sizing arithmetic (for feasibility checks)

- Finished size = stitch count ÷ fabric count, per axis. 140 st on 14-ct Aida
  = 10 in (https://xstitchify.com/cross-stitch-pattern-size-guide/,
  https://www.needlework-tips-and-techniques.com/cross-stitch-calculator.html).
  Add ~3 in per side of margin for framing/hooping.
- Worked examples for this tool's bounds (arithmetic, not a citation):
  - 1000 st @ 14-ct = 71.4 in (181 cm) per side; @ 18-ct = 55.6 in (141 cm).
  - 150 st ("Large") @ 14-ct = 10.7 in — a normal project.
  - 10 st @ 14-ct = 0.7 in.

## 5. Colour-reduction / quantization science

- **Confetti** = "isolated single stitches surrounded by different colors — the
  chart equivalent of noise"; it makes a pattern slower and harder to stitch.
  Real converters run an explicit post-quantization cleanup pass that folds
  isolated stitches into the most common surrounding colour, usually with an
  adjustable cluster-size threshold
  (https://stitchmate.app/photo-to-cross-stitch,
  https://phototopattern.com/, https://stitchpatternmaker.com/photo-to-pattern).
  → Cell-averaging *before* quantizing removes source-pixel noise, but does
  **not** remove confetti created at the stitch level, where a cell's averaged
  colour lands in a different cluster than all its neighbours. These are two
  different mechanisms and only the first is addressed by box-averaging.
- **k-means requires squared Euclidean distance.** The centroid (arithmetic
  mean) is the point minimising average *squared Euclidean* distance to a
  cluster's members; Lloyd's algorithm's update step is only valid under that
  metric (https://en.wikipedia.org/wiki/Lloyd%27s_algorithm).
  CIEDE2000 is not a metric (it violates the triangle inequality) and Euclidean
  distances in CIELAB are not isometric with it
  (https://www.researchgate.net/publication/256168903_Investigating_Euclidean_Mappings_for_CIEDE2000_Color_Difference_Formula).
  → Using Euclidean Lab (ΔE*76) **inside k-means is the principled choice, not a
  compromise.** Substituting CIEDE2000 into the assignment step of k-means would
  break the algorithm's convergence guarantee, not improve it.
- **Where ΔE*76 diverges from CIEDE2000:** CIEDE2000 adds SL/SC/SH weighting,
  an a* rescaling factor G, and a rotation term R_T that corrects errors in the
  blue region, largest near mean hue ≈ 275°; earlier formulas systematically
  mis-estimated differences "most notoriously near saturated blues" and for
  near-neutral colours
  (https://snki.nl/en/blogs/kleurverschilformules-uitgelegd-cie76-cmc-cie94-ciede2000,
  https://metricgate.com/docs/delta-e-ciede2000/).
  Practical consequence for palette extraction: ΔE*76 over-weights differences
  at high chroma (so saturated blues/reds attract more palette slots than they
  perceptually deserve) and under-weights them near neutral (so low-chroma
  regions — notably skin tones — get collapsed into fewer clusters than a
  stitcher would want).
- **If a better-than-CIE76 metric is wanted later, the correct move is a
  Euclidean-uniform *space*, not a non-Euclidean formula:**
  - DIN99d: a true uniform coordinate space using plain Euclidean distance;
    predicts experimental data only slightly worse than CIEDE2000 and much
    better than CIE94/CMC (Cui et al., "Uniform colour spaces based on the
    DIN99 colour-difference formula", Color Research & Application 2002 —
    https://onlinelibrary.wiley.com/doi/abs/10.1002/col.10066).
  - Oklab (Ottosson 2020): designed so Euclidean operations behave
    perceptually; fixes CIELAB's blue hue/lightness non-linearity; fitted to
    MacAdam-ellipse and Luo-Rigg data; simple, invertible, CSS Color 4
    (https://bottosson.github.io/posts/oklab/,
    https://en.wikipedia.org/wiki/Oklab_color_space).
  Either drops in as a same-shape replacement for `rgbToLab` +
  `labDistanceSquared` with no change to the k-means loop.
- **Averaging must happen in linear light, not gamma-encoded sRGB.** sRGB is
  non-linear; averaging encoded values shifts the result away from the true
  mean radiance and produces darkened, muted, occasionally hue-shifted output.
  The rule is: convert to linear before any pixel arithmetic, convert back
  after (https://www.ericbrasseur.org/gamma.html,
  https://blog.johnnovak.net/2016/09/21/what-every-coder-should-know-about-gamma/,
  https://entropymine.com/imageworsener/gamma/).
  Canonical demonstration: a 50/50 black-and-white checkerboard averaged in
  gamma-encoded sRGB gives ~128; the physically correct answer is linear 0.5 →
  sRGB ≈ 188. Error is maximal exactly where a photo has fine high-contrast
  detail — the case a cross-stitch downsample hits constantly.
- Box-filtering (area averaging) is otherwise the *correct* prefilter for
  decimation and is strictly better than nearest-neighbour sampling; the
  concern is the colour space it is performed in, not the filter itself.
- k-means vs median-cut/octree for palette selection: k-means converges to
  genuinely representative colours at higher cost — appropriate when the cost
  is irrelevant (Celebi, "Improving the performance of k-means for color
  quantization", Image and Vision Computing 2011 —
  https://faculty.uca.edu/ecelebi/documents/IMAVIS_2011.pdf;
  http://www.leptonica.org/color-quantization.html).

### 6. Reference material added by this review

#### 6.1 OKLab numeric scale — what the constants actually mean

- **A just-noticeable difference in OKLab is ΔE_OK ≈ 0.02.** OKLab's ranges are
  0–1 where CIELAB's are 0–100, so ΔE_OK numbers land at roughly 1/100 of ΔE00;
  the commonly-reported personal JND clusters around 0.02
  (https://news.lavx.hu/article/what-s-my-e-ok-jnd-a-deep-dive-into-human-color-perception,
  https://www.keithcirkel.co.uk/too-much-color/). Treat 0.02 as a working
  rule-of-thumb, not a standardised threshold — no CIE-equivalent standard
  exists for OKLab.
- **Anchor points computed directly from `lib/color.ts` (arithmetic, not a
  citation):** OKLab L of sRGB grey 128 = **0.600** exactly; white = 1.000;
  black = 0.000. So an OKLab distance of 0.4 ≈ mid-grey→white; 0.02 ≈ 1 JND;
  0.2 ≈ 10 JND.
- **OKLab is not as good at *discrimination* as CIEDE2000.** OKLab was fitted
  for appearance uniformity against CAM16 synthetic data, not against
  observer-rated colour-difference data. Measured STRESS on COMBVD (3,813
  pairs): **Oklab 47.35 vs CIEDE2000 29.13**; on BFD-P D65 (2,028 pairs),
  **Oklab 51.45 vs CIEDE2000 24.12**. The paper attributes the gap to Oklab
  underperforming specifically on chroma- and hue-dominant pairs
  (https://arxiv.org/html/2606.05255v1). Raph Levien's review raises no
  correctness objection beyond the cube-root transfer function and near-black
  contrast (https://raphlinus.github.io/color/2021/01/18/oklab-critique.html).
  → Practical consequence for this project: OKLab remains the right *space*
  (it is Euclidean, which Lloyd's algorithm requires — see §5 above), but its
  distances are noticeably less reliable for saturated and hue-dominant pairs
  than CIEDE2000. Any threshold expressed in OKLab distance is therefore
  approximate to within roughly a factor of ~1.6 in STRESS terms, which is a
  reason to keep such thresholds conservative.

#### 6.2 ICM / Potts model

- ICM (Besag, "On the statistical analysis of dirty pictures", JRSS-B 48(3)
  1986, pp. 259–302,
  http://www2.stat.duke.edu/~scs/Courses/Stat376/Papers/GibbsFieldEst/BesagDirtyPicsJRSSB1986.pdf)
  is a greedy coordinate-ascent: cycle through sites, replace each site's label
  with the one maximising the local conditional probability *given the current
  values of its neighbours*, until a full sweep changes nothing. **Convergence
  is guaranteed under serial (sequential) updating** and is rapid; the result
  is a local optimum only, and depends strongly on the initialisation.
  (PDF text was not machine-extractable in this session; this statement is
  taken from secondary summaries of the paper — https://en.wikipedia.org/wiki/Iterated_conditional_modes
  and the search-result summary of Li, *MRF Modeling in Image Analysis*, ch. 8,
  https://nlpr.ia.ac.cn/users/szli/mrf_book/Other_Chapters/Chapter_8/node135.html,
  which was unreachable for direct fetch. Verify against the paper before
  relying on the exact wording.)
  → The guarantee rests on each accepted update **not increasing a single
  global energy**. If the pairwise term is not symmetric between the two sites
  of a pair, no such global energy exists and the guarantee lapses.
- **Sequential visiting order matters.** Standard practice for ICM-family
  solvers is to alternate the scan direction (traverse the ordered site list
  forwards then backwards) or use a chequerboard/coding partition, rather than
  a fixed raster order, to avoid a directional bias in how information
  propagates (search summary of the Li MRF-book ICM chapter, cited above —
  **uncited beyond that, recalled standard practice; verify**).
- **Potts model = minimal total perimeter.** The Potts pairwise term
  θ_uv(s,t) = λ[s ≠ t] makes MAP inference equivalent to "partition the image
  domain with minimal total boundary length"
  (https://arxiv.org/pdf/2001.09017, https://arxiv.org/pdf/1501.03771).
  It is *not* submodular for ≥3 labels even with λ > 0.
- **Shrinking bias is the documented failure mode of a strong Potts smoothness
  term.** Because the objective penalises boundary length, over-regularisation
  systematically "excludes thin structures for the sake of a compact object";
  thin, elongated structures are the hardest case
  (http://www0.cs.ucl.ac.uk/staff/s.vicente/papers/connectedGC-CVPR08-TR.pdf,
  https://link.springer.com/chapter/10.1007/978-3-642-23626-6_68,
  https://en.wikipedia.org/wiki/Graph_cuts_in_computer_vision).
  → Directly relevant: 1–2-cell-wide features (catchlights, eyelashes, wires,
  lettering strokes, thin highlights) are exactly what a strong smoothness
  weight erases.

#### 6.3 Sobel

- The Sobel kernel's [1 2 1] smoothing makes it *less* noise-sensitive than
  Roberts, but it "still amplifies high frequencies" and produces noisy output
  on images containing Gaussian noise; natural edges also come out several
  pixels wide, and the operator struggles on finely textured surfaces
  (https://homepages.inf.ed.ac.uk/rbf/HIPR2/sobel.htm).
- Gaussian pre-smoothing before the gradient is the standard remedy for false
  edges from noise and compression artefacts; JPEG specifically introduces
  block effects in flat areas and edge noise ("mosquito") along high-contrast
  edges (https://homepages.inf.ed.ac.uk/rbf/HIPR2/sobel.htm, and the JPEG
  artefact characterisation in
  https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/7532767).
- **Numeric scale (arithmetic, not a citation):** with 8-bit input, a hard
  black↔white step gives |g| = 4 × 255 = 1020; the theoretical maximum is
  4·255·√2 ≈ 1443. For i.i.d. pixel noise of σ levels, the Sobel response has
  sd = √12·σ ≈ 3.46σ per component, so the *maximum* over N pixels in one
  stitch cell is ≈ 3.46σ·√(2 ln N) — e.g. ≈ 12σ for N = 400. Max-over-N is an
  extreme-value statistic and is therefore upward-biased; the bias grows as
  √(log N) with the downsample ratio.
- **Luminance-only gradients are blind to isoluminant chromatic edges.** A
  red/green boundary of matched luma produces ~0 Sobel response. The
  principled fix is a multi-channel (Di Zenzo structure-tensor) gradient, or
  at minimum the max of per-channel gradients — cheap here since `rgbToOklab`
  already exists. (**Uncited — recalled standard knowledge; verify against
  Di Zenzo 1986, "A note on the gradient of a multi-image".**)

#### 6.4 Saliency-weighted quantisation

- Allocating quantisation finely in salient regions and coarsely in flat ones
  is an established technique; weight values derived from homogeneity and
  distinctiveness maps can be folded directly into a weighted k-means cost
  function (https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0263729,
  https://arxiv.org/pdf/2002.04988, https://arxiv.org/pdf/2602.20650).
  → Relevant because this project computes an importance map and then uses it
  *only* for assignment, never for palette selection.

#### 6.5 Digital compactness (P²/A)

- P²/A is the classical compactness descriptor, but in the digital domain
  digital shapes have boundaries of measurable width, and both perimeter and
  area change under rotation; different perimeter definitions give different
  values, so raw P²/A on a pixel grid is biased and not rotation-invariant
  (https://ieeexplore.ieee.org/document/1300173,
  https://ietresearch.onlinelibrary.wiley.com/doi/abs/10.1049/el.2013.3685).
  → P²/A is usable as a *relative* metric between two runs of this pipeline at
  the same grid size; it is not comparable across grid sizes and has no
  absolute "good" value.

#### 6.6 Craft domain — what stitchers actually complain about

- **Confetti is worst at colour transitions, not scattered at random.** "The
  worst confetti happens at transitions between colours. Where a dark area
  meets a light area in your photo, the pixels in between are shades of grey
  that don't cleanly belong to either colour" — producing "a messy band of
  isolated stitches along every edge"
  (https://xstitchify.com/cross-stitch-confetti/).
- **Some confetti is legitimate.** "A small amount of confetti is normal and
  sometimes necessary for detail. The problem is when confetti dominates the
  pattern." Xstitchify explicitly makes confetti removal a *human-steered
  brush* rather than a global rule, on the grounds that distinguishing
  important detail from noise is a judgement call
  (https://xstitchify.com/cross-stitch-confetti/).
  → Corroborates this project's importance-weighted approach in principle, and
  argues that an automatic pipeline should err toward under-cleaning near
  high-importance areas.
- **Practical colour counts: 10–15 for a manageable project, 15–30 ideal, ~40
  the practical ceiling for faces.** "Beyond that you're adding colours the eye
  can't distinguish while creating confetti in skin and hair areas."
  (https://stitchmate.app/guides/how-many-colors-for-cross-stitch — reached via
  search snippet; direct fetch returned HTTP 403, same as the M4-era
  stitchmate pages.)
  → The tool's MAX_COLORS = 64 is above the craft-practical ceiling.
- **Banding is the known cost of *not* dithering.** "With only a handful of
  thread colours, a smooth gradient has to band into visible stripes because
  each row jumps to the next-nearest available colour"; error diffusion is the
  standard remedy, at the cost of exactly the confetti this project is trying
  to remove (https://xstitchify.com/cross-stitch-confetti/, and the search
  summary of https://stitchmate.app/guides/best-photos-for-cross-stitch).
  → D6's rejection of Floyd–Steinberg is defensible, but banding is then an
  *accepted trade-off to document*, not an unexpected defect.

### 7. Findings against the implementation

#### (a) Real bugs / unsound choices — should be fixed

**A1 — The fine pass's pairwise energy is repulsive above edge strength 0.474.
(Established; provable from the defaults.)**
`lib/local-optimizer.ts:82-96`. For candidate colour `c` at cell `i`, the code
adds `smoothness·(1−e)` per *mismatched* neighbour and `edgeLoss·e` per
*matched* neighbour. Subtracting the per-cell constant `Σ_n edgeLoss·e_n`
(which does not depend on `c`) shows the construction is **exactly equivalent**
to a single Potts term with effective coupling

    β(e) = smoothness·(1 − e) − edgeLoss·e

applied to mismatches only. With `DEFAULT_MULTI_SCALE_WEIGHTS.fine`
(`local-optimizer.ts:125`, smoothness 0.045, edgeLoss 0.05), β(e) < 0 for
e > 0.045/(0.045+0.05) = **0.474**. A negative Potts coupling is an
anti-ferromagnetic / repulsive interaction: the energy is then *minimised by
disagreement*, and the model will pay up to 0.05 in squared OKLab distance
(≈ 0.224 OKLab ≈ 11 JND of colour error) to make a cell differ from its
high-edge neighbour. Confirmed by direct calculation (2026-09-09): at e=0.474,
β≈0; at e=0.7, β=-0.0215; at e=1.0, β=-0.05. Consequences:
- Boundary cells one step outside a strong edge are pushed off their true
  nearest colour, displacing silhouettes by up to one stitch toward the
  high-importance side.
- Frustrated/checkerboard configurations become locally favourable — which
  `fixDiagonalConnections` then cleans up afterwards, masking the cause.
Note the coarse pass is safe: its crossover is e = 0.09/0.10 = 0.9.
Also note `edgeLoss` is not an independent knob at all — it is a
reparameterisation of the smoothness weight. **Fix:** replace the two branches
with the single equivalent term `β(e) = max(0, smoothness·(1−e) −
edgeLoss·e)`, charged on mismatches only. Same behaviour where the current
defaults are sane, no repulsive regime, one fewer illusory parameter.
**STATUS: FIXED 2026-09-09 — see HANDOVER.md D11.**

**A2 — Palette colours are never recomputed after optimisation.
(Established; a straightforward accuracy loss.)**
`lib/quantize.ts:136` computes each palette entry as the linear-light mean of
its *k-means* cluster. `lib/pattern.ts:39-45` then reassigns a large fraction
of cells via ICM + component recolouring + diagonal fixes, and
`lib/palette-optimizer.ts:73` keeps the survivor's original colour on a merge
rather than the count-weighted mean of the merged pair. Nothing anywhere
re-estimates a palette entry from the cells actually assigned to it. So the
colours the user prints and stitches are the pre-optimisation centroids of a
membership that no longer holds. **Fix:** after all cleanup/merge passes and
before symbol assignment in `pattern.ts`, recompute each surviving palette
entry as the linear-light mean of its final member cells (reuse
`meanRgbLinear`). This is one Lloyd update, it provably cannot increase
`averageReconstructionError`, and `lib/diagnostics.ts:105` already measures the
improvement. **STATUS: FIXED 2026-09-09 — see HANDOVER.md D11.**

**A3 — The ICM energy is not a well-defined global energy.
(Established; breaks the convergence guarantee the module's own docblock
cites.)** `lib/local-optimizer.ts:75,96`: `protection = 1 − cellImportance[i]`
multiplies the *whole* boundary term, so pair (i,n) costs `(1−imp_i)·V` when
evaluating `i` and `(1−imp_n)·V` when evaluating `n`. ICM's monotone-descent
guarantee (Besag 1986, §6.2 above) requires a single global energy, which an
asymmetric pairwise potential does not admit — so oscillation between passes is
possible in principle and `MAX_PASSES = 8` (`local-optimizer.ts:20`) silently
absorbs it. Note the `edge = max(imp_i, imp_n)` factor is *already* symmetric
and already encodes "don't over-smooth near important cells", so the extra
asymmetric `protection` factor is largely redundant with it. **Fix:** drop the
`protection` multiplier from the boundary term (keeping the symmetric `(1−e)`
modulation), or replace it with the symmetric `1 − max(imp_i, imp_n)`. Either
restores a genuine global energy and makes the "ICM" label accurate.
**STATUS: FIXED 2026-09-09 — see HANDOVER.md D11 (dropped `protection`
entirely; the eye-highlight detail-preservation test still passes because
`edge = max(imp_i, imp_n)` already carries cell i's own high importance into
every one of its boundary terms).**

**A4 — Sobel importance normalisation is not robust, in both directions.
(Established; this is the failure mode the hand-tuning was least likely to
catch.)** `lib/edge-map.ts:45-47` divides the whole gradient field by the
image's single largest gradient.
- *High-contrast source* (any hard black/white boundary, lettering, a
  specular highlight, a JPEG block edge): max ≈ 1020 while ordinary
  photographic edges sit at 100–300, so real structure normalises to 0.1–0.3.
  With `importance = 0.7·edge + 0.3·contrast` (`edge-map.ts:95`), reaching the
  `importanceProtectionThreshold` of 0.5 (`contour-cleanup.ts:87`) needs
  edge ≥ 0.71 at zero internal contrast, or ≥ 0.63 at contrast 0.2. **On a
  typical photo that threshold essentially never fires**, so
  `recolorSmallComponents` runs as a full-strength, edge-blind confetti eraser.
  Likewise the A1 repulsive regime needs edge ≥ 0.68 — confined to the image's
  very strongest edges, i.e. exactly the silhouette.
- *Low-contrast source* (fog, flat/backlit lighting, an overcast landscape):
  the strongest real gradient may be ~100 while per-cell noise maxima reach
  ~12σ ≈ 36 (§6.3), so flat noisy areas normalise to ~0.35 importance,
  protection drops to ~0.65, and confetti suppression weakens across the whole
  image. This is precisely the "genuinely low-contrast photo" case the M8
  brief asked about, and the synthetic test images — where the feature under
  test *is* the strongest gradient in frame, so it normalises to ≈ 1.0 —
  cannot surface it.
**Fix (three cheap parts):** (i) normalise by a high percentile of the gradient
histogram (95th–99th) and clip to [0,1] rather than by the single max;
(ii) subtract an absolute floor corresponding to a couple of 8-bit levels so
noise cannot be promoted to "edge"; (iii) use a percentile or mean of gradient
within each cell instead of `cellMaxEdge` (`edge-map.ts:79`), which is an
upward-biased extreme-value statistic. Optionally add a small Gaussian
pre-blur before Sobel, per §6.3. **STATUS: (i) and (ii) FIXED 2026-09-09 —
see HANDOVER.md D11, including a real regression the first attempt at (i)
caused (98th percentile was too aggressive for images with substantial
real texture/noise, not just outliers — shipped at 99.9th instead, caught
by re-measuring confetti ratio, not assumed correct from the math alone).
(iii) deferred — mean-within-cell is a bigger behavior change needing
separate visual re-verification; logged as open work.**

**A5 — The gradient is luminance-only, so isoluminant colour edges are
invisible. (Established.)** `lib/edge-map.ts:15,81` reduce to
`luminance()` (`lib/color.ts:70`) before differencing. A red/green boundary of
matched luma yields ~0 importance, so the optimizer will smooth straight across
it — a common case in flowers, foliage, and clothing. **Fix:** compute the
gradient on OKLab (all three channels, magnitude = √(gL²+ga²+gb²) per
direction, or the Di Zenzo structure tensor). `rgbToOklab` already exists.
Minor related note: `luminance()` applies Rec.709 *linear-light* coefficients
to gamma-encoded values — that is luma Y′, not luminance Y. Acceptable and
conventional for edge detection; but for the dark-to-light palette sort at
`pattern.ts:76-77`, OKLab L would be the consistent choice given the rest of
the pipeline. **STATUS: DEFERRED — a real, meaningful improvement but a
bigger change (redoes the whole edge-map module's per-pixel loop in OKLab
instead of luminance); logged as open work rather than rushed.**

**A6 — Three copies of "the" energy function, one of which differs, so the
passes minimise different objectives.** `local-optimizer.ts:80-96`,
`simulated-annealing.ts:67-79` (identical), and `contour-cleanup.ts:155-163`
(**not** identical: it charges a flat `options.smoothness` per mismatched
boundary pair, with no `(1−edge)` discount, no `edgeLoss` term and no
`protection` factor). This is the direct, mechanical answer to "can these
passes fight each other": yes — a small component sitting *on* a real edge is
protected by ICM's edge discount and then recoloured away by
`recolorSmallComponents`, which cannot see the edge. The
`importanceProtectionThreshold` guard is the only defence, and per A4 it rarely
fires. Compounding it, `DEFAULT_COMPONENT_RECOLOR_OPTIONS.smoothness = 0.045`
(`contour-cleanup.ts:86`) is a hand-copied literal that can silently drift out
of sync with `DEFAULT_MULTI_SCALE_WEIGHTS.fine.smoothness`. **Fix:** extract one
exported `pairEnergy(importance, i, n, sameLabel, weights)` and have all three
passes call it; derive the component-recolour smoothness from the same weights
object. Then the fixed sequence really is coordinate descent on one objective
and the passes provably cannot undo each other.
**STATUS: FIXED 2026-09-09 — see HANDOVER.md D11 (new `lib/energy.ts`
shared by all three passes).**

**A7 — `fixDiagonalConnections` is the last structural pass, is
importance-blind, and can *increase* confetti with nothing after it to clean
up.** `lib/contour-cleanup.ts:15-73`, invoked at `pattern.ts:45`.
- It has no importance term at all, unlike every other pass. A 1-cell-wide
  diagonal line — a whisker, a rope, a mast, a lettering stroke, an eyelash —
  is *by construction* a chain of 2×2 anti-diagonal pinches, so it triggers on
  every block along the line. Because the two candidate directions (erase the
  line cell, or thicken it into the background) have near-symmetric OKLab
  costs, which way each block resolves is close to a coin flip on source
  values, giving a ragged half-erased/half-thickened diagonal.
  (A clean 45° *staircase boundary between two regions* is correctly not
  matched by the predicate at `contour-cleanup.ts:41` — verified by hand. The
  problem is specifically thin diagonal *features*.)
- It applies its cheapest candidate unconditionally (`contour-cleanup.ts:64`),
  with no "leave it alone" option, even when `bestCost` is large and positive.
  Every other pass in the pipeline compares against the status quo.
- Recolouring one member of a pinch can leave the other member as a size-1
  component, and since this runs after `recolorSmallComponents` and before only
  `mergeSimilarColors` (which can never create a mismatch), there is no pass
  left to clean it up. So the final pipeline stage can regress `confettiRatio`.
**Fix:** add the same `importanceProtectionThreshold` guard used by
`recolorSmallComponents`; add "do nothing" as a candidate with a cost ceiling;
and either re-run `recolorSmallComponents` (or one ICM sweep) after it, or
iterate the cleanup pair to a fixed point.
**STATUS: FIXED 2026-09-09 — see HANDOVER.md D11 (importance guard + cost
ceiling added; `recolorSmallComponents` re-run once after diagonal fixes).**

**A8 — `maxComponentSize: 6` is an absolute constant on a grid whose area
varies by four orders of magnitude.** `contour-cleanup.ts:85`. `MIN_STITCHES`
is 10 and `MAX_STITCHES` is 1000 (`lib/types.ts:40-41`), so grids range from
~70 to ~667,000 cells. Six cells is genuinely nothing at 667k cells and is
**8.6% of a 10×7 pattern** — at 50 stitches ("Small" preset,
`types.ts:35`) a 6-cell region is a whole eye or mouth. **Fix:** scale it, e.g.
`clamp(round(cellCount · f), 1, 6)`, or simply cap it at 2–3 below ~2,500
cells. Same argument applies to `confettiRatio`'s `maxOrphanSize = 2`
(`regions.ts:97`) as a *metric*, though that one is only reported, not acted
on, so it matters less. **STATUS: FIXED 2026-09-09 — see HANDOVER.md D11.**

**A9 — The smoothness weights make the colour term nearly inert, and this is
much stronger than D6's "small loss in raw per-cell colour accuracy" implies.
(Reasonable approximation, but mis-described — and the magnitude should be
a deliberate choice, not an artefact of hand-tuning.)** Working in OKLab units
with the §6.1 anchors: switching a fully-surrounded cell to its neighbours'
colour saves 4 × 0.045 = 0.18 of energy, so it is accepted for any squared
colour-error increase below 0.18, i.e. a colour move of up to
**√0.18 = 0.424 OKLab ≈ 21 JND — larger than mid-grey→white**. For a cell with
two mismatched neighbours the budget is √0.09 = 0.30 OKLab ≈ 15 JND. Adjacent
palette entries in a 64-colour photographic palette are typically ~0.02–0.05
OKLab apart (squared: 0.0004–0.0025), i.e. **50–450× smaller than the
smoothness term**. **STATUS: DEFERRED — a real, well-argued point, but the
suggested fix (scale-relative smoothness) is a bigger design change than a
bug fix and deserves its own validation pass rather than being bundled into
the A1/A3/A6/A7/A8 correctness-bug batch. Logged as open work in
HANDOVER.md D11.**

**A10 — Importance is used for assignment but never for palette selection.
(Established gap, per §6.4.)** `lib/quantize.ts` runs unweighted k-means over
cells; `edge-map.ts`'s importance is computed *after* (`pattern.ts:37-38`) and
only reaches the optimizer. k-means allocates centroids by frequency × spread,
so large uniform fields (sky, skin, background) win palette slots and small
salient features get none. **STATUS: DEFERRED — a real gap but a moderate
feature addition (touches k-means++ seeding and the centroid update), not a
bug in existing behavior. Logged as open work in HANDOVER.md D11.**

#### (b) Confirmed sound — leave alone

- OKLab + squared Euclidean inside k-means, k-means++ seeding, the
  convergence threshold (0.01 OKLab = half a JND), the palette-merge distance
  threshold (0.02 OKLab = exactly one JND), restricting component-recolor
  candidates to adjacent colors, using already-updated neighbor values in
  raster order (correct ICM, not a bug), evaluating every palette entry per
  cell (correct conditional-mode search), linear-light averaging, the
  component→cells index fix, the zero-count palette compaction, rejecting
  Floyd-Steinberg, and deferring simulated annealing (further reinforced:
  its iteration count doesn't scale with grid size, so at 1000 stitches it
  would touch ~3% of boundary cells once — logged as a caveat if it's ever
  wired in).

#### (c) Legitimate nice-to-haves — not blocking

- Alternate the ICM scan direction per pass; fix a tie-break bias toward
  palette index 0; an exact (not approximate) ICM speedup via a color-term
  lower-bound prune; directional (not scalar-max) edge strength using the
  already-computed gx/gy; an importance-weighted reconstruction-error
  diagnostic (catches losing a 3-cell catchlight that a mean-over-all-cells
  metric can't see); craft-facing diagnostics (components per color,
  distinct colors per 10x10 block); surfacing the actually-delivered color
  count in the UI when merging reduces it well below what was requested.

### 8. Confidence and gaps

High confidence, derivable from the code and arithmetic alone: A1
(confirmed by direct calculation), A2, A3, A6, A7, A8, A9's numbers, and the
OKLab anchor L(sRGB 128) = 0.600. High confidence, well-sourced: Potts
shrinking bias, Sobel noise behavior, the craft facts in §6.6, OKLab's
STRESS gap vs CIEDE2000. Medium confidence: the ΔE_OK ≈ 0.02 JND figure is a
repeated blog-post rule of thumb, not a CIE-style standard; Besag 1986's
exact wording on serial-update convergence couldn't be extracted (PDF not
parseable); the alternating-scan-direction remedy is recalled practice,
not directly sourced. This review was static (no build/test run) — A1, A2,
A4, and A7 all predict visible effects that were then verified empirically
via the project's own test suite and real headless-browser runs (see
HANDOVER.md D11), not just taken on faith.
