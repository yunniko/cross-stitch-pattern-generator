What is new is the migration step: one place that brings a file of any earlier version up to date, and refuses a file from a later one by name. The file on disk stays one grid; it becomes layers, with a raised version and a migration, in the goal that adds a second layer. ### G-099 · Generation is extensible: settings declared once, the pipeline as stages — DONE (2026-10-05, deployed 2026-10-05, Owner sign-off 2026-10-05)
- **What:** asked by the Owner, 2026-10-05: "can we make algorithms of generation expandable too, as we did with tools?" Two parts. (1) A generation setting is declared once (id, kind, values or range, default, how it is sent) and the settings store, its control, the request, the processor's validation and Rust's parser all read that declaration (architecture step 5). (2) The pipeline in `rust/cs-core/src/pattern.rs`, one 773-line function that branches on the modes, becomes named stages behind one contract (sampling, photo adjustment, colour reduction, edges, dithering, lines, texture strokes, thread matching); each mode is one registered implementation, and the pipeline is assembled from the settings.
- **Why:** a new generation setting is edited in seven places in three languages today (`docs/architecture.md`, placement guide), and a new algorithm means editing the one long function every other mode lives in.
- **Acceptance criteria:** the 74 golden hashes unchanged, so every existing chart generates byte for byte as before; generation time measured before and after; a new setting and its algorithm added as one declaration and one Rust module, shown by a temporary one and then removed; no visible change.
- **Constraints:** the algorithms run in Rust on the server, so an extension is a module compiled into the build, not something loaded while the app runs (own plugins only, D281). The combinations that are refused today (dithering with Crisp edges, for one) must stay refused, from the declarations.

### G-100 · Dithering is extensible: a pattern is one module, written once — DONE (2026-10-07, deployed 2026-10-07, Owner sign-off 2026-10-07)
- **What:** asked by the Owner, 2026-10-05. Today a dither pattern exists twice: in Rust, which makes the chart (`rust/cs-core/src/dither.rs`, `dither_hand_drawn.rs`), and again in TypeScript (`lib/pipeline/dither.ts`, `dither-hand-drawn.ts`), which draws the preview in the photo settings; its id is in two lists, its label and group in the photo settings, and a pattern with settings of its own (as the drawn marks have) has its editor written by hand. The goal: (1) a pattern is one Rust module behind one contract (its id, its settings, its arithmetic) in a list, as overlays are; (2) the preview is drawn by that same code, so nothing is written twice; (3) a pattern's name, group and settings are declared once and the chooser and its settings are drawn from the declaration.
- **Why:** a threshold-matrix pattern is already only data (D198), but any other new pattern is two implementations that must agree, three lists and hand-written interface.
- **Acceptance criteria:** the 13 existing patterns produce the same charts (golden hashes, `scripts/measure-generation.ts`) and the same previews (compared pixel for pixel before and after); a new pattern added as one Rust module and one declaration, shown by a temporary one and then removed; the preview of a pattern without settings appears no slower than today, and the wait for a pattern with settings (now a request to the server) is measured and reported.
- **Constraints:** **Where the preview comes from is decided (Owner, 2026-10-05):** "By default dithering should have precompiled images, it doesn't need to dither every time. If dithering is parametrical as hand drawn one, let it just be dithered at server side." So a pattern without settings of its own has its preview made once, when the app is built, by the Rust that makes charts; a pattern with settings asks the server for its preview when a setting changes. The TypeScript copies of the patterns go. Old charts record the pattern they were made with by id, so ids never change.
- **Architecture fit (review, 2026-10-06):** this goal closes a gap the architecture names (section 2: dither patterns are not behind a contract). (1) The contract and the list in Rust follow `Overlay` and `OVERLAYS` (`rust/cs-core/src/overlay.rs`, D294). (2) TypeScript still has to know each pattern's id, label, group and settings, for the feature list (D303), `lib/features/in-force.ts`, `lib/features/request-check.ts` and the chooser. With the TypeScript patterns gone that knowledge has one source: Rust's declaration written out as data when the app is built, as D198's matrices are generated, with a check that the committed file is current. A TypeScript list typed by hand beside the Rust one would be the two-lists problem again. (3) The built preview images follow the same rule (committed, with a check in CI that they are current), so that building the web app does not need the Rust toolchain; settled in planning and recorded as a decision. (4) The preview request for a pattern with settings is a route like the others: `guardMutation`, the feature check by name, and an entry in G-109's list of limited actions if that goal has landed. (5) A pattern's settings are drawn from its declaration through the generation-settings contract (`lib/pipeline/generation-settings.ts`, D293). The drawn marks' editor needs a custom control: one named escape in the contract, not a branch on the pattern's id in the chooser.
- **Answered (Owner, 2026-10-06):** "Dithering should have pregenerated pictures, the same bw as it is now (now it does not seem to be generated from picture)." The Owner's observation is right, and the review's question was worded wrongly: today's larger preview (`app/components/dither-preview.tsx`) is not made from the photo. It is the pattern in two tones over a fixed dark-to-light ramp, and the chart enters it only through its size. Read as: for a pattern without settings, the ten tiles and the larger preview are both pictures made when the app is built, in the same two tones over the same ramp; the chart's size no longer enters them. "The same way" in the note below therefore holds.
- **What follows (review):** (1) D206 and D208 are superseded for the patterns without settings, by a decision file written when this goal changes the code, since they are still true of it today. (2) A matrix pattern's picture does not depend on the chart's size (D208), so its preview stays the same pixel for pixel. A kernel pattern's corner depends on the chart's width, so its built picture is the pattern at one fixed size, chosen in planning; the acceptance's "same previews, pixel for pixel" is compared at that size, and for a chart of another width the picture may differ slightly from today's. (3) The drawn marks keep their preview at the chart's own size, drawn by the server (Owner, 2026-10-05), with the click that reshuffles them.
- **Noted by the review, not proposed:** `rust/cs-wasm` (D186, a benchmark, nothing ships) could draw previews in the browser from the same Rust; the Owner chose built pictures and the server.
