### G-103 · The three workspaces are features: Generation, Edit and Export each switched with its tab — DONE (2026-10-06, deployed 2026-10-06, Owner sign-off 2026-10-07)
- **What:** asked by the Owner, 2026-10-06. Generation, Edit and Export become features in the G-102 list, each one switch covering both the work and the way in: the workspace's tab and everything inside it. Hidden: the tab is absent and the workspace cannot be reached by any road (key, command list, link, a request to the server). Locked: the tab is shown greyed with its note. On, Locked or Hidden for the site, a person, a feature set, guests or accounts, as every other feature.
- **Why:** G-102 made the workspaces core (`feature: null`), so today a tier can withhold single generation settings or export kinds but not a whole stage; the Owner wants a stage as one switch.
- **Acceptance criteria (draft):** each of the three appears in `/admin/features` as one entry; Hidden and Locked hold for the tab, the keys and commands that open it, and the server routes behind it (generate, export), refused by name; the features inside a workspace keep their own switches, and a workspace switched off wins over them; with all On, the browser suite passes unchanged.
- **Constraints:** a chart already open keeps its data whatever is switched off (G-102's rule: never damage a chart). Admin pages are never exercised against the live site (standing rule).
- **Answered (Owner, 2026-10-06):** with Generation off, a person starts a chart as a new empty chart or by opening an existing one. When the workspace a person would land in is off, the next one that is on opens. When all three are off (not a normal state, possible in an emergency), a window says so with an error, instead of an empty editor.
- **Answered (Owner, 2026-10-06):** a control belongs to the workspace whose tab it is on: the photo settings and Crop on the Edit tab are Edit's; if they are also offered on the Generation tab, there they are Generation's.
- **Architecture fit (review, 2026-10-06):** the workspace list is the registry (`WORKSPACES` in `lib/editor/workspaces.ts`, D297). (3) The server's side is one mapping from a workspace to the requests behind it, read by `lib/features/request-check.ts` (Generation: jobs, colour recommendations, photo upload; Export: exports), not a check written into each route. (4) The places that assume Photo is always there go through one "first workspace that is on" rule in `lib/editor/workspaces.ts`: `workspaceShown`, `workspaceOpen`, `firstTools` (which throws when a workspace offers no tool), the starting value in `app/hooks/use-editor-view.ts`, and the `workspace` column of `REPLACE_PLANS` (`lib/editor/document-replace.ts`). (5) The three `view.workspace-*` commands (`app/commands/registry.ts`, `feature: null` today) name their workspace's feature. ### G-105 · Release versions, release notes, and a process that keeps them current — DONE (2026-10-06, deployed 2026-10-06, Owner sign-off 2026-10-07)
- **What:** asked by the Owner, 2026-10-06. (1) The app carries a release version (today `package.json` reads 0.1.0 and nothing shows it): each deploy is a numbered release, tagged in git, shown in the app. (2) Release notes per release, written for users (what changed, not commits), shown in the app as "What's new". (3) The development process changed so that a change which alters what a user sees updates the next release's notes in the same commit, enforced by a check, not a promise.
- **Split (confirmed by the Owner, 2026-10-06):** this goal first held the user guide and comments on its pages as well. The guide is now G-112, taken up after the goals that change the interface; comments are G-111, with the moderation G-108 needs.
- **Why:** users have no record of what changed.
- **Acceptance criteria (draft):** the version shows in the app and matches a git tag and a deploy-log row; every release since the scheme starts has notes; `docs/development-loop.md` and the fast lane (D280) name the step.
- **Constraints:** nothing published elsewhere without the Owner's approval (VALUES): the notes live in the app itself.
- **Answered (Owner, 2026-10-06):** versions are numbered the usual way, semantic versioning (major.minor.patch).
- **Answered (Owner, 2026-10-06):** the version stays 0.x until the public launch.
- **Architecture fit (review, 2026-10-06):** (1) Release notes are one small file per change, gathered at release. The check (in `npm run check` and CI) fails a change that alters what a user sees and carries neither a note nor an explicit "nothing a user sees" mark; what counts as such a change is fixed in planning, and the fast lane (D280) names the same step. (2) The version has one source, `package.json`; it reaches the app as the commit does today (a build argument beside `APP_COMMIT` in the `Dockerfile`), and the release step makes the tag and the deploy-log row from it. (3) Notes are content files drawn by one renderer under `app/`, the one G-112's pages will use. A Markdown renderer would be a new dependency: a stack decision to record.
- **The acceptance restated (planning, 2026-10-06):** (1) the app shows its version, and that number is the one in `package.json`, in the git tag `v<version>` on the deployed commit and in the deploy-log row. (2) Every release from the first one under the scheme has notes in a user's words, read in the app under "What's new". (3) A change to what a user sees cannot pass the fast check or CI without a note or an explicit mark that there is nothing to see. (4) `docs/development-loop.md` names the step in both lanes, and a decision that names D280 records it.
- **Fixed in planning (2026-10-06; each becomes a decision file when built):** (a) **What counts as a change a user sees:** any change under `app/` (but `app/admin/`), `lib/`, `rust/` or `public/`, test files apart. The rule goes by path and errs on asking, since a rule that tried to judge the change itself would be guessed around; a change there with nothing to see says so. (b) **The mark is a file, not a line in the commit message:** a note of the kind `internal` with one line of reason, beside the notes of the kinds `new`, `changed` and `fixed` in `release-notes/next/`. A file can be checked before the commit exists and by CI alike; a line in the message can only be checked after. Internal notes are dropped when a release is gathered. (c) **The version is read from `package.json` when the app is built** (`next.config.ts`), with no second build argument that could disagree with it; this is simpler than the review's "argument beside `APP_COMMIT`". The constant `APP_VERSION` in `lib/editor/crash-report.ts` holds the commit today and is renamed for what it is. (d) **Numbers:** the first release under the scheme is 0.2.0 (0.1.0 was never shown or tagged; there are no tags today). While 0.x: a release with a `new` or `changed` note raises the middle number, one with only `fixed` notes the last. (e) **Where it shows:** the version, with the commit, at the foot of Preferences (application scope, `docs/interface-placement.md`), with a link to "What's new"; "What's new" is a page of its own (`/whats-new`) and a command in the command list. The app does not announce a release unasked. (f) **Markdown** is drawn on the server by `marked`, which the portfolio already uses (`listing-studio`); the notes are the project's own files, never a user's text.
- **To confirm with the plan (Owner):** (a), (d) and (e) above are judgments, the Owner's to change; the plan runs on them unless told otherwise.
